**11月23日 · 瓦片四角边框断开修复 + 尺寸定稿 82×82**

- 提示词（用户要求 + 截图）：
  "修复边框四个角断开的问题，并将瓦片尺寸调整为 82px。确保瓦片在四个角处无缝衔接、
  边框连续闭合，同时所有瓦片的宽高统一为 82px，保持整体布局对齐、无间隙、无重叠，
  并在调整后验证视觉效果正常。"
- 根因定位：roundRect 路径本身是标准 arcTo 写法（排除路径缺陷），真正的元凶是
  **图标 PNG 为不透明白底矩形**——80×80 的图片边距瓦片边仅 2px，而圆角 r=12 的弧线
  距瓦片角最近处只有 ~3.5px，图片四角的白底正好盖住弧线 → 边框"四角断开"。
- 修复（render.js drawNotes 绘制顺序重排）：
  ① 图标绘制前 save→roundRect→**clip**：图片被裁剪在圆角路径内，白底矩形角不再外溢；
  ② **描边移到最后**（restore 之后）：边框永远压在图标之上，即使内容再满也盖不住弧线；
  ③ 瓦片 84→**82×82**（内容区 (TW-4)=78px），圆角 12 不变。
- 方法论：先验证"路径生成是否正确"再找覆盖物——间隙类视觉 bug 常是**层序问题**
  （谁盖住了谁），不是几何问题；canvas 多元素绘制时，边框/描边一律放最后画。
- 验证：截图确认四角连续闭合无缺口、瓦片 82×82、图标与名称清晰、判定/桶区/HUD 正常；

**11月23日 · 键盘活性实测检测（hasFocus 不可靠，提示条改为"没收到按键就一直挂"）**

- 提示词（用户反馈）：合并同步 master 后"现在是按键盘完全没有响应"。
- 排查：① 全局错误探针 ERR=0、scene=playing；② 顶层窗口派发真实 KeyboardEvent
  → score=100，键盘链路完好；③ 搭 iframe wrapper 模拟预览面板——合成事件进 iframe
  也能判定（score=100），但 **hasFocus=false**，物理键盘事件只会投递给持有焦点的父页文档。
  结论：上一版修复依赖 document.hasFocus() 显示提示条，但部分嵌入环境该值不可靠，
  导致提示没出现，用户无从自救。
- 我的修改：input.js 新增 keyboardAlive（开局置 false，收到任意真实 keydown 置 true，
  每局 refocus 时重置）——用"实测有没有收到按键"替代"焦点状态推断"；ui.js 提示条件
  改为 `playing && (!keyboardAlive || !hasFocus)`：只要键盘真没通，提示条一直挂着；
  refocus 补 window.focus()；提示条加呼吸动画更醒目；v=18。
- 验证：STAGE1（进游戏不按键）hint=SHOWN alive=false；STAGE2（派发真实 keydown）

- 教训：**环境探测值（hasFocus/UA 等）只能当参考，"实测行为"才是判据**——
  与"探针打 BOOT 标记区分脚本没执行/值不对"是同一方法论。

**11月19日 · "无法完整通关"根因：负 dt → arc 负半径异常打断主循环（本次最有价值的发现）**

- 提示词（用户反馈）：
  "调整第一关：降低下落垃圾密度并放慢速度；同时排查并修复导致玩家无法完整通关的问题
  （如关卡结束条件、判定异常或流程中断等），保证正常操作下每局都能顺利通关，并验证难度曲线。"
- 排查过程（拟人模拟驱动，一层层剥出来的）：
  ① 先查结束条件/判定/结算链路——代码逻辑全部正确（node 构造通关态实测
  `LS={"0":1888}` 等均通过）；
  ② 写"拟人玩家"模拟（±120ms 反应、6% 按错桶）跑无头 Edge，发现部分局卡在
  `S=playing done=42/42 lives=2`——音符全判完、命没扣光、时间已过尾音，**就是不结算**；

  **`IndexSizeError: Failed to execute 'arc': radius (-355.9) is negative`**。
- 根因链（两个独立缺陷叠加）：
  ① `main.js` 的 `dt = Math.min((now-lastFrame)/1000, 0.05)` 只限上限不限下限。
  rAF 帧传入的是 vsync 时间戳、看门狗补帧传的是 performance.now()，两者交错时
  `now-lastFrame` 为负 → dt<0 → `fx.update(dt)` 让特效时间倒流（e.t<0）；

- 我的修改：
  ① `dt = Math.max(0, Math.min(dt, 0.05))` 双向限幅（root fix）；
  ② `effects.js` 画环半径 `Math.max(r, 0.5)`、alpha `Math.max(0, 1-p)` 防御（belt & braces）；
  ③ 看门狗改为**常驻**：每帧布防 600ms，rAF 饿死就补帧（旧版只在开局查一次，
  "偶尔触发但不持续"的 rAF 环境下循环照样会饿死）；
  ④ 难度：第一关 density 0.85→0.5、speed 170→150（此前实测生成 ~70 颗、0.6 秒一颗，
  新手 3 命撑不完）；同时发现 L2/L3 用 0.5 拍网格会生成 140/221 颗（0.42/0.31 秒一颗）
  同样不可通关 → step 统一改 1 拍，曲线理顺为平均间隔 1.2/0.85/0.63 秒、
  音符 41/70/111 颗、理论最高分 5250/9630/15750。
- 验证：修复前模拟 5 局有卡死；修复后 **5 局全部正常结算**（done=N/N、剩命 1~2、
  分数 2300~3200）。教训（答辩重点素材）：
  **① 时间增量必须双向限幅**——混合多种帧源（rAF 时间戳 / performance.now()）时

**11月18日 · 契约级时间基准错误：attach 叠加 startTime 导致下落延迟（最核心的一条）**

- 提示词（用户反馈，两次表述相反，实为同一 bug 的两个侧面）：
  "开头时有时很久才有垃圾下落" / "重开一局后出现 ready go 后马上下落垃圾…应在提示出现时立即
  开始下落垃圾，去掉当前的延迟等待。"
- 根因（用页面内探针实测定位，不是猜）：`audio.getTime()` 返回**相对时间**
  `t = ctx.currentTime - startTime`（开局为 −2），但 `chart.attach()` 按契约注释写成**绝对时间**
  `hitTime = startTime + offset`。判定与绘制都取 `dtn = hitTime - t`，于是
  `dtn = offset + 2×startTime - currentTime`——**多算了一整份 startTime**。
  两个可观测后果：① 首颗垃圾到线时间被推迟 2×startTime（新开页面约 4 秒）；
  ② startTime 随页面打开时长单调增大（stop() 不冻结 ctx），**每重开一局延迟更长**，
  这解释了"有时很久"和"重开时等很久"的随机性。
- 定位过程：无头浏览器截图看到瓦片在 y≈-30 边界闪烁、箭头已画但瓦片不画 → 注入标题探针
  打印 `T / hit0 / N`，发现 `T=0.70` 时 `hit0=3.20`（期望 1.20）→ 反推公式立刻定位到 attach。
- 我的修改：
  ① `chart.attach(notes)` 改为 `hitTime = offset`（与 getTime 同基准，相对时钟起点），
  与 BGM 节拍严格对齐；main.js 同步改调用；② 前奏恢复契约值 2 拍；③ 版本号 v=6。
- 验证：探针 `T=0.70 / hit0=1.20` 正确；三帧截图——READY 显示期间垃圾已从顶端滑入、
  GO 阶段瓦片在半屏、之后"漏接"红色反馈与进度条正常推进。
- 教训（答辩可讲）：**跨模块契约里"绝对时间/相对时间"必须指名单位与基准**，注释写"绝对"
  而调用方用"相对"，语法检查、纯逻辑单测（我之前的 node 模拟是直接按 hitTime 按键，绕过了
  真实时钟差）都发现不了，只有做"端到端时间轴"验证才暴露。
